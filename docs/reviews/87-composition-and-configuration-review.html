taitube-platform @ 1cbb39a · 2026-09-23

How dependencies are wired and how configuration reaches the code that needs it, read from source after tickets 82 and 84 landed. Every claim carries a file:line and was re-read before it was written down. Baseline: pnpm test:architecture is green — 19 files, 109 assertions, 991 ms.

Outcome: ticket 87.

1. The question that started this

Should dependency injection become global, the way it is in C#, NestJS or Angular, instead of passing objects explicitly?

Passing objects explicitly is not the problem. It is the reason 45 unit tests can build a service with exactly the collaborators the case needs, and it is what makes the hexagon real rather than documented. The problem is that the passing is optional, so the wiring the composition root performs is not the wiring that runs. Eleven services read process.env behind the caller's back, six construct a collaborator the caller forgot to hand them, and one builds a concrete adapter class from inside apps/api.

That is a service locator wearing a constructor. A global container built on top of it would inherit every one of those fallbacks and hide them one layer deeper. The order matters: make the dependencies total first, then give them one registration surface.

4. What a container should and should not buy

Five things make DI in .NET, NestJS and Angular feel like infrastructure rather than plumbing. Four of them are worth having here. The fifth is the one that costs a runtime dependency, and it is the one that buys least.

What those frameworks give Here today Verdict
One registration surface (ServiceCollection, @Module({providers})) Three, two disagreeing (F5) Take it. One module per layer, shared by both apps.
Lazy resolution — only what is reached is constructed Everything, eagerly, 32× (F6) Take it. A memoised factory per token is four lines.
Declared lifetimes (singleton / scoped / transient) Implicit; two process-wide singletons (defaultPaginator, getMetrics()) Take the half that pays. Singleton-per-container plus ordered dispose(), which is also the fix for F2. Request scope has no consumer — the caller is already an argument.
Test overrides (overrideProvider().useValue()) Already good — buildApp({ adapters }) Keep. Same ergonomics, one override(token, value).
Constructor injection by type, resolved through reflection Hand-written new X({…}) Leave it. See below.

Why not the decorator kind

  • It needs reflection. @Injectable() resolving by type requires emitDecoratorMetadata and a reflect-metadata polyfill in the eager path of both deployables. TC39 standard decorators carry no parameter types, so that ecosystem is pinned to the legacy flag indefinitely.
  • It is a dual-runtime bet. Rule 2 requires worker code to behave identically under vitest and bun test. Decorator metadata emission is exactly the class of transpiler-level behaviour that rule exists to keep out.
  • It trades a compile error for a runtime one. Forget reactionCache today and TypeScript names the call site. Through a string- or symbol-keyed registry you find out when the route runs — unless tokens carry their type, which is the cheap half of the idea and needs no decorators.
  • 45 unit tests would get worse. new VideoService({ videos, authorization }) is one line and says precisely what the case touches. Test.createTestingModule is the NestJS tax for the same thing.
the whole mechanism — no dependency, no reflection, no cast
export interface Token<T> { readonly name: string; readonly _t?: (x: T) => T }
export const token = <T>(name: string): Token<T> => ({ name });

export class Container {
  provide<T>(t: Token<T>, make: (c: Container) => T): this   // registration
  get<T>(t: Token<T>): T                                      // lazy, memoised, cycle-detecting
  override<T>(t: Token<T>, value: T): this                    // tests
  dispose(): Promise<Result<void, ShutdownFailed>>            // reverse construction order
}

// registration reads like a @Module, and the compiler checks every edge
c.provide(Storage,      (c) => c.get(Config).kind === 'in-memory'
                                 ? new InMemoryStorageClient()
                                 : new S3StorageClient(c.get(Config).s3));
c.provide(VideoService, (c) => new VideoService({
  videos:        c.get(Repositories).videos,
  authorization: c.get(Authorization),
  paginator:     c.get(Paginator),
  reactionCache: c.get(ReactionCache),
  probeQueue:    c.get(Queues).get('probe'),
  cdn:           c.get(Config).cdn,
}));

get returns T with no cast, because the token carries the type. The registration module is the single global surface that was missing. Nothing about it is Fastify-specific, so apps/worker registers the same adapter half and adds its own stages — which is what deletes F5.

At the transport edge there is a second, smaller move with the same shape: Fastify already has a container. app.decorate('services', …) plus one declare module 'fastify' — the mechanism request.user already uses at plugins/auth.ts:32-36 — retires thirteen hand-written *RouteOptions interfaces and lets every route module become a plain plugin registered from one table. That is what makes the awaits uniform (F7), rather than choosing a side.

Six statements, five of which exist only because the deps type is optional. Making the type total deletes the body entirely — and the two fields that survive are not fields at all.

6. Worked example: buildApp

Four jobs are braided into one function: resolving configuration, constructing the object graph, registering HTTP, and starting background work. Splitting them is what answers the await question, because the question only looks odd while the other three jobs are in the way.

JobTodayBelongs to
config4 options + 2 raw process.env reads at app.ts:52-53, then 11 more downstreamloadEnv() at the process entry, once
graphresolveAdapterSet + createServiceSet, both eagerContainer registration modules, lazy
http13 bespoke calls, 2 return shapes, 5 awaitsone table of Fastify plugins, one await app.register each
lifecycle2 pollers started inside the builder; onClose closes 2 of ~12 resources; no signal handlerstart() / container.dispose(), driven by main.ts

On the awaits specifically: app.register() is deferred — Avvio runs the boot queue at ready() or listen(), in registration order either way. Awaiting forces that step to run now, which only matters when the next line reads something the plugin installed. No line in buildApp does. So the five awaits are neither wrong nor load-bearing; they are the residue of thirteen registration calls that were never given one shape. Make every route module a plugin and the answer is the same for all of them.
