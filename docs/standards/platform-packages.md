# Platform packages

How the reusable packages under `packages/platform/` are built and changed. The rule they all serve: **another app
installs them and finds none of this product in them.** Each rule below that a machine can check is checked, and the
check is named beside it. Tier and layer rules are in [packages/AGENTS.md](../../packages/AGENTS.md).

## Platform or app

A package is **platform** when a second app could use it unchanged: it names no product value (a cookie, a locale,
an env key, a route, a metric prefix, an error code of this product), and it asks for what varies. Otherwise it is an
**app package** under `packages/<tier>/`. Ask first, before the tier and the layer. A package that is half of each is
two packages: the generic half moves to `packages/platform/<tier>/<name>` (`@kit/<name>`), the app half keeps its
`@vp/<name>` name and depends on it.

The directory is the scope, as it is the tier: `packages/platform/<tier>/<name>`, name `@kit/<name>`. `vp.layer` and
the tier rules apply to platform packages unchanged. `docs/package-map.md` lists every package, generated by
`pnpm gen:package-map` from the manifests.

## The holy rule

**A `@kit/*` package never depends on, imports or names a `@vp/*` package.** Not in `dependencies`,
`devDependencies` or `peerDependencies`, not in an import or `vi.mock(import())`, a tsconfig path, an alias or a
`setupFiles` string, and not in a README, `AGENTS.md`, CHANGELOG, comment or test string. There is no allowlist, no
pending-move allowance and no dev-edge carve-out. `pnpm boundaries` fails on an edge, and
`platform-never-names-app.test.ts` fails on the substring `@vp/` in any tracked file under `packages/platform/`.

When a platform package needs something the app owns, invert the dependency (below). When the needed piece is
itself generic, move it into a `@kit` package with `git mv` and rewrite its importers. Never copy it. Docs say "the
app", "the app's error registry", never a package name.

## Parameters before tokens

A value the app hands a platform package is a **required, typed parameter** (a function argument, an option, a
prop): a missing one fails to compile, and a default would be this product's value in disguise. Use a `@kit/di`
token only where a container resolves the value (`Token<T>`, `createRegistry().provide(...)`, the server
`Container`), such as the error code registry, the catalogues and the runtime tokens (`Clock`, `Random`, `EnvSource`,
`Fetch`, `CookieJar`). A token with no sensible default is required: a missing provision is a startup error, never a
silent English or `'taitube'` fallback.

## `define*` and `provide*`

A package that holds data exports a typed `define*` helper (`defineErrorCodes`, `defineKeyspace`, `defineKind`,
`defineTokenSet`) that returns a frozen value, and `provide*` helpers that wrap a value for a registry. It exports no
instance, runs nothing at import time and reads no global: `platform-no-import-time-registration.test.ts` fails a
top-level `provide*`, `define*` or `register*` call whose result is dropped. The app calls them once, in its
composition root (server: `apps/server/*/src/composition/`; client: each app's `src/router.tsx` and `src/routes/__root.tsx`). A
function takes the registry or the value it needs as an argument; no function body looks one up from a global.
A spec swaps a value with `createRegistry().provide(Token, fake)`, with no `vi.mock` of an import.

## Extension only

New behaviour arrives as a new token, a registry entry, a plugin (`defineKind`) or an option whose default keeps the
old behaviour. Existing behaviour changes only with a major version. A library never edits a list another app owns:
open for extension because any app builds its own registry, closed for modification because no package edits one.

## The public surface

Each package has an `exports` map with `.` and, where meant, `./contract`. Nothing else resolves:
`platform-no-deep-imports.test.ts` fails an import of `@kit/<pkg>/src/...` or any subpath the map does not list, and a
relative import that leaves a package root.

`pnpm gen:api` writes the surface (exported names with their types) to `api/<name>.api.txt`, and the CI step
`pnpm gen:api --check` fails on a diff, so a change to the surface is a reviewed diff. Never edit the file by hand.

## Semver and deprecation

`version` in `package.json` is real: `0.x` while the API settles, `1.0.0` once a second app has used it. Every package
keeps a `CHANGELOG.md` with an entry for its version. A diff in `api/*.api.txt` without a changelog entry and a version
bump fails `pnpm check:platform-changes` (against `origin/main`; CI passes `--base HEAD^1`). A removal needs an earlier
`@deprecated` that names the removal version, and one release of overlap.

## Type safety

Strict generics; branded types where they prevent a mix-up;
discriminated unions that end in `assertNever`; registries checked with `satisfies`. `platform-type-strictness.test.ts`
bans `any`, a type assertion other than `as const`, a non-null `!` and `@ts-ignore` in platform source, with no
exception list: the fix is a type, a guard or a schema.

Every public generic has a type-level spec in `src/__tests__/type-fixtures/` (`expectTypeOf` for what it infers,
`// @ts-expect-error` for what it rejects, each directive failing for exactly the reason its comment names). `@kit/ui`
has one for its exports with a type parameter (`lazyComponent`, `createCompoundContext`, `variantNames`);
`@kit/components`, `@kit/web-testing` and `@kit/vite-preset` export no generic, and the components' plain props are
held by their component specs.

Misuse must fail to compile, and a spec proves it: every public generic has a **type-level spec** under the
package's `src/__tests__/type-fixtures/`, written with `expectTypeOf` and `// @ts-expect-error`. The package's
`typecheck` compiles it (a universal or client package through `tsconfig.spec.json`), so an `@ts-expect-error` on code
that now compiles fails the build.

## Dependencies and build

A platform package's `dependencies` are other platform packages only. Third-party libraries (`zod`, `pino`,
`@casl/ability`, React, OpenTelemetry, `prom-client`) are `peerDependencies`. Every package is `sideEffects: false`
and ESM only. `platform-manifest.test.ts` holds the manifest shape: `exports`, `types`, `version`, `CHANGELOG.md`,
`README.md`, `AGENTS.md` with its `CLAUDE.md` symlink, `api/<name>.api.txt`, and a `tsconfig` that extends only
`@kit/tsconfig`.

No platform package holds copy: no catalogue, no `dt(` call, no user-facing English string
(`platform-no-copy.test.ts`). The app supplies every word.

## Contract suites

A platform package that defines a port or a registry exports a `./contract` suite, `runXContract(makeImpl)`, with
vitest as a peer dependency. The repository's own implementations (the in-memory doubles, the app's registries) run
it against themselves, and so does any other app against its own. Changing a suite is a change of the surface, so it
needs the version bump and the changelog entry. No platform package exports `./contract` yet: the per-port suites live
today in `packages/server/adapters/__tests__/contract/` (layout in [testing.md](testing.md), section 2) and move with
`@kit/ports`, which lands as the last step of ticket 170.

## Extractable, and the second app

A platform package must work outside this repository. `pnpm check:extractable [<package>|second-app]`
(`scripts/check-extractable.ts`, its parts in `scripts/extractable/`) proves it for every package under
`packages/platform/`: it copies the package and its platform closure, computed from the manifests, to a temporary
directory outside the repository, installs offline and frozen from the repository's lockfile cut down to that
closure, builds it and runs the package's own `typecheck` and `test` there. It fails on a `@vp/` reference, on a path
that leaves the package folder, and on a link or compiled file that resolves outside the temporary directory.

`second-app` installs `tests/fixtures/second-app/` (outside the workspace globs) from packed tarballs. It
registers its own error codes, `fi-FI` and right to left `ar-EG`, another cookie prefix, key namespace, metric prefix
and dev-token issuer, builds its registry and runs its spec, and the check fails when an installed package's code
holds a value of this product. After changing the second app's dependencies, run
`pnpm check:extractable second-app --refresh-lockfile`. CI runs the check as the `extractable` job, one shard per
platform package plus `second-app`, inside the budgets of [testing.md](testing.md), section 9.

## What fails the build

| Rule | Check |
|---|---|
| No platform edge to an app package | `pnpm boundaries`, `platform-never-names-app.test.ts` |
| No product value in platform source | `platform-no-app-data.test.ts` |
| No copy in a platform package | `platform-no-copy.test.ts` |
| No deep import | `platform-no-deep-imports.test.ts` |
| No registration at import time | `platform-no-import-time-registration.test.ts` |
| Manifest shape | `platform-manifest.test.ts` |
| No `any`, assertion, `!` or `@ts-ignore` | `platform-type-strictness.test.ts` |
| A surface change is reviewed and versioned | `pnpm gen:api --check`, `pnpm check:platform-changes` |
| It works outside the repository | `pnpm check:extractable` (`scripts/check-extractable.ts`), the `extractable` job, `tests/fixtures/second-app/` |

[ARCHITECTURE.md section 6](../../ARCHITECTURE.md#6-verification--enforcement) lists what each assertion plants and
catches.
