# AGENTS.md — @vp/studio (Creator Studio)

Instructions for any coding agent working on the Taitube creator studio (`apps/client/studio`): the creator
surface (upload, edit, and the library, analytics and admin panel the tickets after 93 add), served and deployed
apart from the viewer app.

> Owner: ticket [93](../../../docs/tickets/93-creator-studio-separate-app.md) · the shell, library and editor:
> [60](../../../docs/tickets/60-creator-studio-dashboard-video-management-ui.md) · the admin panel: [61](../../../docs/tickets/61-admin-control-panel-category-moderation-ui.md)

---

## 1. The same stack as web

Everything in [apps/client/web/AGENTS.md](../web/AGENTS.md) applies here: TanStack Start over Vite 8 and React 19,
file routes under `src/routes/` with a committed `src/routeTree.gen.ts`, TanStack Query filled by loaders, TanStack
Form, the `#app/` import alias, the design system from `@vp/ui`, the two Vitest projects and the Playwright suite in
`e2e/`. Its rules (declarative authorization, the API client from router context, rules from packages, formatting
through `@vp/intl-react`, nothing phones home, one spec per source, MSW typed by the contracts) hold here word for
word. This file lists only what differs. The folder layers, the component folder and the names both apps share are
[docs/standards/frontend-structure.md](../../../docs/standards/frontend-structure.md).

The React Compiler compiles it as it does web. One more Vitest project, `vitest.uncompiled.config.ts`, runs the
`*.differential.dom.test.tsx` specs (the upload dialog) without the compiler against the compiled run's snapshot.

`apps/client/studio` is **tier `client`, layer T6**, like web. It depends on the same client packages; a module both
apps need lives in one of them, never in a copy (`tests/architecture/client-app-duplicates.test.ts` fails a source
file byte-identical between the two apps).

## 2. What differs

| Concern | Studio |
|---|---|
| Origin | `http://localhost:5174` for `dev`, `vite preview` and `start`; `studio.localhost` on k3d, `studio.<domain>` in cloud (SDD §11, §12) |
| Config | `src/lib/config` is the only reader of `import.meta.env`: `VITE_API_BASE_URL`, `SSR_API_BASE_URL` and `VITE_COOKIE_DOMAIN` as web reads them (through `resolveApiBaseUrl` and the env schemas in `@vp/queries`), plus `VITE_WEB_URL` (default `http://localhost:5173`), where the viewer app is |
| Routes | `/` redirects to `/videos`; `/videos` (the library, its sort, page and title filter in the address), `/videos/$videoId/edit` (the metadata editor), `/analytics` (the channel's figures and daily views) and `/videos/$videoId/analytics` (the same for one video, plus its retention), both with the range (`7d`, `30d`, `90d`, `lifetime`) in the address, `/live` (the creator's broadcast: credentials, viewers, chat moderation, stop), `/team` (the channel's members, pending invites and audit log, behind `canReadChannelTeam`; `tab`, `actor` and `action` in the address), `/invites` (the viewer's own invites to other teams; `invite` in the address), `/comments` (the inbox of comments on the creator's videos, `all`, `unanswered` or `reported` in the address, each row answered, hearted or pinned in place; the navigation marks it when `comment.created` arrives elsewhere), and `/upload` (it opens the upload dialog over the library) and `/customization` under the `_authed` layout, plus `/upload/edit/$videoId`, which redirects to the editor; `/videos/$videoId` (a video address with nothing after it redirects to the library), `/admin/categories`, `/admin/curation` (the picks of the day), `/admin/moderation` and `/admin/queues` under `_authed/admin`, whose `beforeLoad` evaluates `canAccessAdmin` (a denial redirects to `/?denied=admin`, which the shell turns into a toast); `/login`, the studio's own sign-in; `/live/overlay/$token`, the OBS browser source (`?widget=chat|alerts|goal`), public on the overlay token alone and rendered bare, since its `staticData.bare` makes `StudioShell` return the `<Outlet />` with no workspace, upload dock or widget; nothing else public |
| Shell | `src/features/shell/components/studio-shell/studio-shell.tsx`, composed by `src/routes/-components/studio-root/studio-root.tsx` (the `__root.tsx` page) on every page: `StudioWorkspace` (`src/components/workspace/studio-workspace/`) with the skip link, the navigation, the toolbar (the logo, the account through `shell-account-menu.tsx`) and the page in its content; the library's inspector opens beside the page for a selected row. The shell imports no other feature: `StudioRoot` hands it the `navigation` (`ActingNavItems`, told whether a comment arrived), `toolbarAction` (`ActingUploadAction`, the upload button for a role that may upload) and `inspector` (`VideoInspector`) slots, and wraps it in `ActiveChannelProvider` and `UploadDockProvider` (`features/upload/components/upload-dock/`), so the upload dialog (opened from the navigation, the toolbar or `/upload`) and `UploadWidget` (byte progress, then each rendition's and the thumbnail's progress from the user event stream) outlive every page the creator moves between |
| Guests | the session cookie is the one web reads (SDD §11), so a creator signed in on web is signed in here; `_authed`'s `beforeLoad` sends a guest to the studio's own `/login?redirect=<path>`, never to web, and back once signed in |
| Appearance | the account menu's **Appearance** submenu (`shell-account-menu.tsx`) is `AppearanceMenuGroups` from `@vp/ui` (theme, mode, density over `useAppearance`, which writes the cookie web shares through `VITE_COOKIE_DOMAIN`) and a link to `${WEB_URL}/settings/appearance` for the rest; a guest, who has no account menu, gets the `ThemeMenu` button beside Sign in |
| Channel | `/customization` (`features/channel/`) is a list of independent sections, each a `<form>` of `CustomizationSection` (compound: Root, Header, Title, Description, Body, Footer) with its own `useUpdateChannel` over `PATCH /v1/me/channel`; the page edits the acting channel (`useActingChannel`, `GET /v1/me/channel`, key `['channel','acting',channelId]`), so an editor edits the channel they switched to, and a save writes the session's channel only while the acting channel is the viewer's own: `identity-section` (name, handle with its 30-day cooldown in a `Callout`, description, country `Select`, contact email), `links-section` (up to 8 links with the platform icon read off the host as you type, moved up and down, and the banner button), `spotlight-section` (the trailer and the subscriber video through `SpotlightVideoPicker`, a `Command` over the creator's public ready videos, and a tab per language for its own description and trailer, saved with `PUT /v1/me/channel/spotlight`), `images-section` (picture and banner, no section save: `ChannelImageEditor` per kind puts a `FileField` and the channel-image validators in front of `ImageCropper` (`components/image/`, over `Dialog`: a `SegmentedControl` for desktop, mobile and TV, the safe-area guides, zoom, a live preview of each target), and `useChannelImageUpload` prepares `POST /v1/me/channel/images/:kind/upload`, PUTs the file and completes with the crops in whole pixels of the file, then holds the job as working until the user events `channel.image.ready` or `channel.image.failed` arrive, refreshing the acting channel and the session on ready; Remove sends a `null` `avatarUrl` or `bannerUrl` at once). `start-here-section` (behind `<Can do="pin" on="Video">`) pins up to `FEATURED_VIDEOS_MAX` videos for the channel page's Start here shelf: `StartHerePins` (`SortableList`, drag and keyboard), `StartHerePicker` (a `Command` in a `Popover` over `pickableVideosQueryOptions`, the creator's public ready videos, disabled at six), `StartHerePreview` (`StartHereShelf`, from `@vp/components`) and `useSaveFeatured`, an optimistic `PUT /v1/me/channel/featured` that writes the shelf into the cache at once, rolls it back and toasts the presented error on a refusal. Pins are a draft until Save A new section is one more component in `customization-page.tsx`, nothing else changes. The channel is the session's (`['session']`): a save writes it there and invalidates the router. Handle format runs in the browser (`validateHandle` through `validateWith`); availability is the API's 409, shown on the handle. There is no availability endpoint yet |
| Team | `features/team/`: the acting channel. `ActiveChannelProvider` (mounted by `StudioRoot`) joins the account with `GET /v1/me/memberships` and hands `useActiveChannel()` (`channelId`, `ownerId`, `role`, `own`) to every route, and a `PermissionsProvider` whose user carries those memberships, so `useCan` and `<Can>` judge against the acting channel; `ActingNavItems` shows each page the role reaches (a moderator gets the comment inbox only) behind `ChannelSwitcher` (`DropdownMenu`). The channel is a host-only `vp.channel` cookie behind `createActingChannelStore` (`@vp/queries`, in router context, dehydrated into the page): `@vp/api-client` sends it as `X-Channel-Id` on the contracts marked `channelScoped`, and `_authed`'s `beforeLoad` (`ensureActingChannel`) puts a viewer whose membership ended back on their own channel. `useSwitchChannel` selects, forgets the cache of the channel left and lands on a page the role reaches. `TeamPage` (`Tabs`): `MembersPanel` (`DataTable` with `MemberRoleCell`, `RemoveMemberDialog`, `PendingInvites`, `InviteDialog` with `HandleLookup` and `RoleCapabilities`, which read the role table in `@vp/domain`), and `AuditPanel` over the kit's `AuditLogList` and `RoleBadge` (`components/team/`) and `FilterSelect`, `LoadMore` (`components/table/`) with keyset Load more. What a role may give or touch comes from `useRoleRules`, the `@vp/permissions` rules over the acting channel. `/invites` (`InvitesPage`, `InviteCard`, over `useMyInvites` on `GET /v1/me/invites`; `invite` in the address marks the one a `team_invite` notification opened, which web links to) lists the viewer's own pending invites to accept or decline; `InvitesNavItem` in `ActingNavItems` shows it with a count while one waits, and accepting invalidates the memberships, so the switcher lists the channel at once. `LeaveTeamItem` in the `ChannelSwitcher` menu (behind `canRemoveChannelMember` on the viewer's own membership, never on their own channel) opens `LeaveTeamDialog`, and `useLeaveTeam` removes the viewer, then returns to their own channel through `useSwitchChannel` |
| Search engines | `public/robots.txt` disallows everything and `__root.tsx` sets `robots: noindex, nofollow`; no studio route carries SEO meta |
| Copy | studio strings live in `@vp/messages` under the `studio.` prefix (`packages/universal/messages/src/en/studio.ts`); every string of the studio is a key there |
| App kit | `src/components/<area>/<name>/`: `workspace/studio-workspace`, `table/data-table`, `analytics/stat-card` and `analytics/chart-frame` (the frame and the palette helpers; the charts are `features/analytics/`'s). The reference smart wrapper is `features/content/components/library-video-row.tsx`, on `VideoThumbnail` from `@vp/components`. Adding one: [design-system.md](../../../docs/standards/design-system.md) |
| Styles | none of its own: `@vp/ui`'s stylesheet sets the body on the design tokens |
| Upload | `features/upload/`: `uploadVideo` (presigned single or multipart PUTs) reports `{ loaded, total }` bytes, `uploadVideoMutationOptions` writes them to the query cache under the upload's id and `useUploadProgress(id)` reads them; the dialog, the widget and its processing rows read the dock |
| Editor | `features/videos/`: `EditVideoForm` (TanStack Form over `@vp/validation` rules, categories from `GET /v1/categories`, tags as chips, a sanitised markdown preview of the description through `react-markdown`) saves with `PATCH /v1/creator/videos/:id` against the video's `version`; a `VERSION_CONFLICT` opens `VersionConflictDialog` (reload, or overwrite on the newest version) |
| Analytics | `features/analytics/`: `KpiCard` and, for the channel only, `NetSubscribersCard` over `StatCard`; `ViewsChart` (`granularity` `day` over the range, `hour` over the last 48 hours whatever the range) and `RetentionHeatmap` over `ChartFrame` and recharts, on `analyticsQueryOptions(api, scope, range)` (`scope` is the channel or one video), `channelAnalyticsQueryOptions` (the same cache entry, typed with net subscribers) and the shared `videoRetentionQueryOptions`. Each card's `KpiDelta` is `kpiChange` against the response's `previous`: a signed percentage, or a signed count for net subscribers, which can cross zero; none for `lifetime` (no previous period) or a percentage of zero. Each chart's recharts plot is `React.lazy`, so the library loads with the page that draws it, in its own chunk. Series colours come from `seriesColor` and `sequentialScale` only (`series-color.test.ts` holds every series at 3:1 on `surface` in each registry theme and mode); each chart also writes its data as a visually hidden table |
| Batch actions | `features/videos/`: the batch bar in `LibraryTable` (`LibraryBatchActions`) and the row menu delete and visibility share `useBatchActions`, which fans `DELETE /v1/creator/videos/:id` and `PATCH` (against each row's `version`) out per video, since there is no batch endpoint; a partial failure toasts `done of total`, and the failed rows stay selected. Rendered through `useCan`, deletes behind `DeleteVideosDialog` |
| Live | `features/live/`: `LiveDashboard` over `myLiveStreamQueryOptions` (`POST /v1/me/live`, idempotent, polled while idle), `LiveStats`, `LiveViewersChart` (viewer samples from `useLiveVideoEvents`, over `ChartFrame`), `LiveCredentialsCard` (`CredentialField`: the stream key and control token masked, Reveal, Copy through `useCopyField`), `LiveChatModeration` (`useLiveChat` over `API_PUBLIC_URL`, the socket the `/api` proxy cannot carry), `LiveChatModeForm` and `LiveStopButton`, each mutation (`useUpdateLiveStream`, `useStopLiveStream`) writing the stream it returns into `liveKeys.mine()`. The overlay widgets (`OverlayChat`, `OverlayAlerts` with the WebAudio chime in `overlay-chime.ts`, `OverlayGoal` over `nextSubscriberGoal`) poll `liveOverlayQueryOptions` every 10 s and draw in dark colours on a transparent body (`body:has([data-obs-overlay])` in `@vp/ui`'s `base.css`). The `live` colour role appears only through `<Badge tone="live">` while the stream is `LIVE`; the kit parts are `components/live/` (`goal-bar`, `alert-banner`, `chat-card`, `credential-field`) |
| Browser suite | `e2e/`: the upload dialog and widget, the editor reached from the old edit URL, `live.test.ts` (the masked stream key, the overlay without the shell), and the headers and XSS suites from `tests/playwright/security/` pointed at the library, `/upload` and `/videos/$videoId/edit`; `playwright.config.ts` is `clientAppPlaywrightConfig` on port base 5400 |

## 3. Local commands

```bash
pnpm --filter @vp/studio dev         # Vite dev server with HMR on http://localhost:5174; root `pnpm dev` starts it too
pnpm --filter @vp/studio build       # dist/client and dist/server; regenerates src/routeTree.gen.ts
pnpm --filter @vp/studio start       # serves the build on http://localhost:5174
pnpm --filter @vp/studio test
pnpm --filter @vp/studio typecheck   # tsconfig.json (the app), tsconfig.spec.json (specs and vite.config.ts), tsconfig.e2e.json
pnpm --filter @vp/studio test:e2e    # the Playwright suite; `make e2e-studio` is the same
```

The browser calls the studio's own `/api`, which its server forwards to the API with the session cookie's token, as
in web. `/login` offers the demo personas as web's does (`VITE_DEMO_PERSONAS`, `SSR_DEV_TOKEN_URL`; see web's AGENTS.md).
